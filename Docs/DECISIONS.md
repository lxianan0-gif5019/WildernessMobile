# 决策记录

> 只记**会影响后面很多天**的决定，以及当时的理由。
> 三个月后你回头看「为什么当初这么定」，答案在这里。
> 格式：一条一个决定，写清 **理由 / 代价 / 什么时候该重新考虑**。

---

## D1 · 引擎用 Unity 2022.3.62f3c1（原计划 6.3 LTS）

**决定**：工程实际建在 Unity 2022.3.62f3c1 + URP 上，不回退也不升级。

**理由**：装机包里拿得到的就是这个版本，URP 成熟、安卓插件生态稳定；6.3 的新渲染特性对一个手机生存游戏没有决定性收益，升级反而要重做材质和管线。

**代价**：用不了 6.x 的部分新 API；以后如果要用某些新插件，版本下限可能卡住。

**重新考虑的信号**：某个必须用的插件/资源包明确只支持 Unity 6；或者 2022.3 LTS 停止维护后打包出问题。

---

## D2 · 输入走 `InputHub` 单一中转

**决定**：所有游戏逻辑只读 `InputHub` 的静态字段，不直接读 `Input.GetKey`。键鼠和触摸各写一个"适配器"往 `InputHub` 里灌数据。

**理由**：同一套玩法逻辑要同时跑键盘和手机，两套输入各写一遍必炸。加手柄时只需再加一个适配器。

**代价**：多一层间接，调试时要多跳一个文件。

**纪律**：绕过 `InputHub` 直接写 `Input.GetKey` 的代码，在手机上一定失效——这是最容易复发的错误。

---

## D3 · 每个系统只有一个"数据真源"

**决定**：背包只能通过 `Inventory.Add/Spend/Clear` 修改；生存数值只能通过 `PlayerStats.Eat/Drink/Damage` 修改；UI 只读不写。

**理由**：存档、HUD、合成扣料三处都要读同一份数据，一旦有第二个写入口，三者立刻对不上，而且极难查。

**代价**：写起来绕一点，不能图省事直接改字段。

**检验方法**：`ARCHITECTURE.md` 末尾那 4 个问题（存在哪 / 谁写 / 谁读 / 怎么存盘），答不出来就别写。

---

## D4 · 美术路线：环境用 AI，角色不用 AI 直出

**决定**
- 环境（树/石/草/建筑模块/武器道具）：Tripo 图生/文生 3D，预算内批量生成
- 角色：**不**用 Tripo 直出。走 VRoid Studio 自捏 或 买现成商用模型，必要时用 Blender 清理
- Tripo 的积分留给环境和道具，不给角色

**理由**：Tripo 训练数据以物体为主，二次元脸/头发是它的最弱项，十次出一次能看，钱和时间都打水漂。角色的"好看"有 90% 来自眼睛贴图、头发分片、卡通着色，这三样 AI 直出给不了。

**代价**：角色要多花一个晚上到两天；可能要额外 ¥150–300 买模型。

**待验证**：先用 1 个角色跑 POC（Tripo 底模 → Blender 清理 → 重建头发 → 贴图 → 骨架 → 渲图）。成了再批量，不成立刻转 VRoid。

## D5 · 移动端性能预算（写死，不许超）

| 项目 | 上限 |
|---|---|
| 帧率 | 30 FPS（中端安卓） |
| 单角色三角面 | 8k–15k |
| 单角色材质 | 1–3 个 |
| 角色贴图 | 1024²，最多 2048² |
| 同屏角色 | ≤ 3 个（超出要 LOD） |
| 场景树 | 420 棵用 GPU Instancing / 合批，不做单独 Draw Call |

**理由**：开发机是 780M 核显，目标机是中端安卓。美术先按这个预算做，比做完再砍面数省十倍力气。

**重新考虑的信号**：真机实测连 30 FPS 都守不住 → 先砍同屏数量，再砍贴图，最后才砍面数。

## D6 · 预算天花板

| 项目 | 上限 | 现状 |
|---|---|---|
| token（DeepSeek flash） | ¥600 全程 | 已花 ¥10.06，余 ¥15.55 |
| 美术（Tripo 等） | ¥600 全程 | 已充 ¥200 |

**理由**：按实测速率推算，180 天全程 token 约 ¥400–600；美术按 POC 结论再定。

**纪律**：单次充值不超过 ¥200，用 10 天对一次账，避免一次性充太多变成沉没成本。

## D7 · 文档制度：DAILY + ARCHITECTURE + 跟踪看板

**决定**：三份文档各管一件事，不合并
- `DAILY.md`：每天收工写一条，记录"改了什么 + 数据流变化"
- `ARCHITECTURE.md`：模块表和三条主线，加系统时更新
- `STATUS.md`：跨天的进度、里程碑、风险（由跟踪会话维护）

**理由**：一个人的项目，最大的风险不是写不出代码，是三天后忘了自己当初怎么设计的。文档是给未来的自己看的，不是给别人看的。

---

## D8 · 跟踪会话与开发会话分离

**决定**：这个会话只做进度记录、预算对账、风险提醒、方案建议；不主动改游戏代码。

**理由**：改代码会产生大量文件和长上下文，把"记忆"淹没掉。分开之后，跟踪会话的上下文永远干净，随时能回答"现在到哪了"。

**例外**：用户明确说"你来改"的时候。
